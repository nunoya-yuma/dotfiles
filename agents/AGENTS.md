# 作業方針

## Git ワークフロー
- **必ずブランチを切ってから作業する**: mainブランチにいる場合は、ファイル編集前に新しいブランチを作成する。
- コミットメッセージはConventional Commits形式・英語で、変更の本質を簡潔に書く。
- 小さく頻繁にコミットし、論理単位・テスト通過ごとに復旧ポイントを作る。
- コミットはユーザーが差分を確認・承認してから行う。「すすめて」などの続行指示は編集の許可であり、コミットの許可ではない。
- コミットが探索的で散らかってきたら、rebase/amendでの整理をこちらから提案する。force pushはユーザーの明示的な許可がある場合のみ。
- コミット前にはself-reviewスキルを使う。TDDで進める場合はtddスキルから始める。自動起動に任せきりにせず、意識して呼び出す。
- コミット前やタスク完了時にはreflectスキルも使い、セッション中の学びをCLAUDE.md/AGENTS.mdや既存skillに反映すべきか確認する。
- コミット前の検証では、テストだけでなくフォーマッタ・リンタなど、CIで実行されるチェックをすべてローカルで通す。テストが通っていても整形漏れは検出されない。具体的なコマンドはREADMEやCI設定から確認する。

## コードとコミュニケーション
- コード（コメント・変数名）は英語、会話は日本語。
- ユーザーへの質問は1メッセージにつき1つに絞り、やり取りを重ねて詰める。前の回答で次に聞くべきことが変わるため、最も判断に影響する質問から聞き、答えから分かった質問は省く。
- ユーザーのタイピングを減らすため、選択肢で答えられる質問は選択肢形式で聞く（Claude CodeのAskUserQuestionのような選択UIがあれば使う。その場合も1回1問）。推奨案を先頭に置いて理由を添える。
- コードや既存の慣習から判断できることは質問せず、仮定を明示して進める。

## ファイルとドキュメント
- 新規ファイル作成やREADME・設計書等のドキュメント追加は積極的に行う（実装とドキュメントが乖離しがちなため、その場で追従させる）。
- READMEは簡潔に保ち、使い方と全体像だけを書く。設計判断の理由は`docs/decisions/`などのADRへ、特定のコードに関する理由はそのコードの横のコメントへ書く。外部ツールの調査メモのように時間とともに古くなる内容は、判断の根拠として必要なものだけを出典・確認日付きで残す。
- 汎用的なルールはこのグローバルなagent instructionsファイルに書く。プロジェクト固有の情報は各プロジェクトのローカルなCLAUDE.md/AGENTS.mdへ（チームで共有しない個人用の指示は後述の`.private-scratch/AGENTS.md`へ）。
- `.private-scratch/`はリポジトリ直下に置く、git管理外の個人用作業領域（メモ、テストリスト等）。存在しない場合は作成し、中に`*`の1行だけを書いた`.gitignore`を置いて自身を無視させる。リポジトリの`.gitignore`は変更しない。
- セッションの最初の返答をする前に（挨拶や質問への回答だけの場合も含めて）、`.private-scratch/AGENTS.md`が存在すれば必ず読み、そのプロジェクトでの個人用の指示として従う。チームで共有しないプロジェクト固有の指示（自分の作業手順や環境のメモ等）はここへ書く。

## 判断の姿勢
- 時間とともに変わりうる技術仕様（外部ツールの対応状況など）を設計判断の根拠にする場合は、記憶に頼らずWeb検索等で確認する。他のOSS等の実装を根拠として文書を書く場合も、該当ファイル・行を実際に読んで確認し、出典を併記する。
- ツールやコマンドを手順として文書に残す前に、実際に実行して効果を確かめる（dry-run等があれば活用する）。公称の機能説明どおりに動いても、対象データの性質によっては実質的な効果がほとんどないことがある。
