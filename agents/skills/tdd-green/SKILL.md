# TDD: Green

前提: `/tdd-red` で書いた、現在Redになっているテストが1つ存在すること。存在しない場合はユーザーに確認してから進める。

## やること

1. 現在Redになっているテストの内容と失敗理由を確認する。
2. 実装は一度に書ききらない。「TDD as if you meant it」の要領で、以下のサイクルを **1回だけ** 実行する。
   a. テストを実行し、今出ている **そのままのエラーメッセージ**(NameError, AttributeError,
      ImportError, TypeError, アサーション失敗など)を確認する。
   b. そのエラーメッセージが要求する **最小の1行、または最小の変更** だけを加える。
      - 例: 未定義の関数/クラス呼び出し → 中身が`pass`や`raise NotImplementedError`だけのstubを
        1つ追加するだけ。ロジックは書かない
      - 例: 引数の数が合わない`TypeError` → シグネチャに引数を1つ追加するだけ。デフォルト値や
        バリデーションは足さない
      - 例: アサーション失敗 → **そのアサーションだけ** を満たす最小のロジックを追加する。次に
        書くはずのテストケースで壊れそうに見えても、先回りして対応しない
   c. テストを再実行し、結果(次のエラー、またはパス)を確認する。
3. **1サイクル終えたら、同一ターン内で次のサイクルへ進まず、必ずそこで応答を終了する。** この1サイクル
   分の小さい差分と実行結果(次に何のエラーが出ているか)をユーザーに提示し、「次のサイクルに進んでよいか」
   を尋ねて停止する。ユーザーから続行の意思(「次へ」「OK」など)が示された、新しいメッセージが来てから
   次のサイクルを開始する。
4. サイクルを繰り返した結果、テストが通ったら、既存テストも含め全テストを実行し、すべてパスすることを
   確認する。`.nunoya_private/test-list.md`の該当項目にチェックを入れる。最終的な結果をユーザーに
   提示し、ここで停止する。

## 禁止事項

- テストを消す、条件を緩める、期待値を書き換えるなどして無理にパスさせること
- 依頼されていない機能を先回りして実装すること
- 現在出ているエラーメッセージが要求する以上のことを一度に書くこと(例: まだ出ていない次のエラーを
  予測して複数箇所を同時に直す)
- **1サイクル(1エラー確認 → 1修正 → 再実行)を終えるごとにユーザーの確認を挟まず、複数サイクルを
  同一ターン内で連続実行すること**。1サイクルごとに必ず応答を終了する
- 複数のテストケースをまとめて実装対象にすること
- このフェーズでリファクタリングを行うこと(構造改善は `/tdd-refactor` で行う)
- 次のRed(次のテストケース)へ自動的に進むこと。ユーザーが `/tdd-red` または `/tdd-refactor` を呼ぶまで待つ
