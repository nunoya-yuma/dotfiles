# TDD: Red

前提: `.private-scratch/test-list.md`にテストリストが存在すること。存在しない場合はユーザーに確認してから進める。

## やること

1. `.private-scratch/test-list.md`から未着手の項目を **1つだけ** 選ぶ。どれを選ぶかユーザーと合意がなければ確認する。新しいテストケースに気づいた場合の扱いは`tdd`の注意点を参照(選ぶ前に追記する)。
2. そのテストケース1つだけを実装する。既存のテストコードやテストリストの他の項目には触れない。
   - テストコードを書く順序は、Arrange/Actから上に積み上げていくのではなく、まず期待する結果
     (assert)を先に書く。そのassertが要求する値・状態から逆算して、必要なArrange/Actを組み立てる。
   - テストコードを完成させるのに何行も必要になる場合は、一度に書ききらない。1行(またはひとまとまり
     の最小の追加)を書いて実行し、出たエラーを確認する、という1サイクルを実行したら、**そこで応答を
     終了してユーザーに確認を求める**。同一ターン内で複数行分をまとめて追加したり、複数サイクルを
     連続実行したりしない。ユーザーから続行の意思(「次へ」「OK」など)が示された新しいメッセージが
     来てから次の1行に進む。
   - このサイクルの中で、テストが呼び出す関数・クラス・構造体・型がまだ存在せず`ImportError`、
     `AttributeError`、コンパイルエラーなどでテストが実行すらできない場合は、それを解消するために
     必要な**宣言のみ**(関数シグネチャ、struct/class/型の器、フィールド)をプロダクションコードに
     追加してよい。本体は空・no-op・デフォルト値を返すだけに留め、ロジックは書かない。テストコードの
     追加とこの宣言の追加は、どちらもエラー内容に応じて交互に行き来する同じ1サイクルの一部として扱い、
     1つ進めるごとに都度ユーザーに確認を求める。
3. テストが実際に実行され、想定通りの理由でRedになることを確認する(アサーションの失敗、または2で
   追加した宣言・空stubを呼んだ結果としての失敗)。構文エラーや無関係な失敗でRedになっていないかも
   確認する。コンパイルエラーや`ImportError`などでテストがまだ実行できていない状態は、Red完了とは
   見なさない。
4. プロダクションコードにロジックを実装しない(2で追加した宣言・空stubを除く)。
5. 積み重ねた差分をまとめたdiffとテスト失敗の出力をユーザーに提示し、ここで停止する。

## 禁止事項

- 複数のテストケースを同時に追加すること
- プロダクションコードにロジックを実装すること(テストを実行可能にするための宣言・空stubの追加は
  除く。それ以外はユーザーからの明示的な依頼がない限り行わない)
- テストコードやプロダクションコードの宣言を組み立てる途中の1サイクル(1行追加 → 実行 → エラー確認)を
  終えるごとにユーザーの確認を挟まず、複数サイクルを同一ターン内で連続実行すること
- 最初からGreenになってしまうテストを書くこと
- コンパイルエラーや`ImportError`などが解消されていない(テストがまだ実行できていない)段階でRed完了と
  報告すること
- Greenフェーズの作業を先取りすること(宣言・空stub以外のロジック実装)。`/tdd-green` をユーザーが呼ぶまで待つ
