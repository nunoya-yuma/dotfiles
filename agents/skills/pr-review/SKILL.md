# PR Review

## Overview

- 他人が書いたPRをレビューし、ユーザがPRに投稿するためのコメント案を作成する。
- 自分のコミット前のセルフレビューには`code-review`を使う。このskillは「作者の意図を理解したうえで、投稿できる指摘を返す」ことを目的とする。
- 特に**機能的には正しいが、シンプルではない・過剰になっている実装**を見落とさないことを重視する。差分を読み始めると書かれた構造を前提として受け入れてしまいやすい(アンカリング)ため、以下の手順で意図的にそれを崩す。
- レビュー結果はターミナルに一覧で出力するのみとし、PRへの投稿はユーザが取捨選択して手で行う。`gh pr review`等での投稿はしない。
- ユーザとの会話は日本語。PRに書くコメント案の言語は、PR本文・既存コメントの言語に合わせる。

## 手順

以下は GitHub CLI(`gh`)が使える前提で書いている。`gh` が使えない場合は次で代替する。

- 差分: GitHub なら `git fetch origin <base>` と `git fetch origin pull/<N>/head` を順に実行したあと `git diff $(git merge-base origin/<base> FETCH_HEAD) FETCH_HEAD` で取得する。
- PR本文・issue・既存の議論: ユーザに貼り付けてもらう。手順2の最小解は要件から組み立てるため、要件が分からないまま差分を読み始めない。

### 1. 意図の把握(差分はまだ読まない)

- `gh pr view <PR> --comments` でタイトル・本文・リンクされたissue・既存の議論を読む。
- このPRが解決すべき要件を箇条書きで明文化する。本文から要件が読み取れない場合は、それ自体を指摘候補にする。

### 2. 最小解を先に設計する

- 差分を見る前に、関連する既存コードだけを読む。変更対象は `gh pr diff <PR> --name-only` でファイル名だけ確認し、手元のブランチに依存しないよう `git show origin/<base>:<path>` でベース側のコードとその呼び出し元を読む。
- そのうえで「自分ならこの要件をどう最小限で実装するか」を書き出す。
  - 変更するファイル・追加する関数/型・おおよその規模
  - 既存のどの仕組みを再利用できるか
- これがアンカリングを避ける基準になるので、省略しない。

### 3. 差分を読み、最小解と比較する

- `gh pr diff <PR>` で差分を読む。差分外の周辺コードが必要な場合は、作業ツリーを汚さないよう `git fetch origin pull/<N>/head` してから `git show FETCH_HEAD:<path>` 等で参照する。
- 最小解に存在しない要素(ファイル・型・関数・引数・設定項目・分岐・レイヤ)をすべて列挙する。それぞれが指摘候補。
- 規模が最小解より大きく違う場合は、その差がどこから来ているかを説明できるようにする。

### 4. 削除テスト

追加された各要素について「これを消したら何が壊れるか」を問い、**具体的な呼び出し元・要件・テストで答えられないもの**は指摘する。「将来必要になるかも」「念のため」は答えとして認めない。

### 5. 過剰パターンのチェック

以下に該当するものがないか確認する。

- 実装が1つしかないinterface/抽象クラス/トレイト、差し替え予定のない依存注入
- 呼び出し元が1箇所しかない薄いラッパー・ヘルパー・中間レイヤ
- どこからも使われていない、またはデフォルト値でしか使われていない引数・オプション・設定項目
- 型やこれまでの処理で起こりえないことが保証されている状態への防御コード(null チェック、try/catch、フォールバック)
- 同じバリデーション・変換が複数の層で重複している
- 計測の根拠がない最適化(キャッシュ、並列化、独自のデータ構造)
- 標準ライブラリや既存コードで数行で書けることに対する新規依存・自前実装
- 使われない後方互換用のコード、フィーチャーフラグ、非推奨の残骸
- 要件に含まれない「ついで」の機能追加・リファクタリング(別PRに分けるべきもの)
- コードの内容を言い換えているだけのコメント、過剰なログ
- 実装の詳細に結合した、または同じことを重複して確かめているテスト

### 6. 通常の観点

シンプルさとは別に、`code-review`の観点(命名、共通化、セキュリティ、スコープ、APIコメント等)とバグ・エッジケースも確認する。ただし手順2〜5を先に終えてから行う。バグ探しと同時に行うと構造の妥当性を疑う意識が薄れるため。

## 出力形式

- 最初に、手順1の要件と手順2の最小解を短く示す(ユーザが指摘の妥当性を判断する材料になるため)。
- 指摘は重要度順に並べ、それぞれに以下を含める。
  - ラベル: `must`(マージ前に直すべき) / `imo`(提案、作者の判断に委ねる) / `nit`(軽微) / `question`(意図の確認)
  - 位置: `path:line`
  - 指摘内容とその理由
  - シンプル化の指摘では、**縮小版の具体的なコード**を添える(「シンプルにできる」だけでは説得力がないため)
  - PRにそのまま貼れるコメント案
- コメント案は断定より質問形式を基本にする(例: 「この interface は他の実装を予定していますか? なければ具象型を直接使う形でも良さそうです」)。作者が意図を持っている可能性を残すため。
- 良い実装にも触れる。
- 指摘が推測に基づく場合(呼び出し元をすべて確認できていない等)は、その旨を明記する。
