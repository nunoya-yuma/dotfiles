# PR Walkthrough

## Overview

- 他人が書いたPRを、ユーザが自分で理解できるよう対話的に案内する。AIが理解して要約を渡すのではなく、ユーザの理解を目的とする。
- 指摘の一覧を作るのは`pr-review`の役割。このskillでは指摘を作ることを目的にしないが、途中で生まれた疑問や違和感は記録してレビューに繋げる。
- 会話は日本語。PRの取得方法(`gh`が使えない場合の代替を含む)は`pr-review`の「手順」冒頭と同じ。

## 手順

### 1. 要件と最小解の共有

- PRの本文・issueから要件を箇条書きにし、「本来はこの程度で実装できそう」という最小解を短く示す(考え方は`pr-review`の手順1〜2と同じ)。同じセッションで`pr-review`を実行済みならその結果を再利用する。
- PRの構造を説明する前にこれを行う。ユーザがPRの構造をそのまま前提として受け入れないよう、比較の基準を先に持ってもらうため。

### 2. 全体像を示す

- 差分を**変更の意図ごと**に分ける(以下、分けた一つひとつを「変更単位」と呼ぶ。例:「データモデルに〇〇を追加」「呼び出し側の対応」「テスト」)。複数ファイルにまたがる変更も、意図が同じなら1つの変更単位にまとめる。
- 変更単位の一覧を、それぞれの対象ファイルとともに全体像として示す。順序は、中心となる変更 → それに依存する変更 → テストを基本にする。
- 大きいPRでは会話が圧縮されても続けられるよう、この全体像と後述の疑問点を`.private-scratch/pr-walkthrough-<PR番号>.md`に保存し、進捗に合わせて更新する。
- 全体像を示したら、順序や粒度をユーザに確認してから始める。

### 3. 変更単位ごとに案内する

各変更単位について以下を行う。

1. 何を・なぜ変えているかを短く説明し、要となるコードを`path:line`付きで抜粋する。差分全体を貼らない。
2. 最小解との違いがあれば「最小解ならこうだが、PRではこうなっている」と示す。
3. **問いを1つだけ**投げ、ユーザの回答を待つ。次の変更単位へ勝手に進まない。
   - 良い問い: 「なぜここで〇〇にしていると思うか」「この入力だとどう動くか」「これを消したら何が壊れるか」
   - 避ける問い: 変数名や行番号を当てさせるような、理解に繋がらない暗記の確認
4. 回答を受けて、合っている点・ずれている点を具体的に返す。ずれている場合は、コードの該当箇所を示して一緒に確かめる。
5. ユーザや自分が「過剰では」「意図が分からない」と感じた点は、疑問点として記録する。

ユーザはいつでも質問・変更単位の飛ばし・深掘りができる。その場合は問いへの回答を求めず、ユーザの流れに合わせる。

### 4. まとめ

- PR全体を、ユーザの言葉も踏まえて数行で要約する。
- 記録した疑問点を一覧で示し、`pr-review`でのレビューに進むか、作者への質問コメントにするかをユーザに尋ねる。
