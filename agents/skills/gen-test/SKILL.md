# Gen test

## 方針

- 指示のあった機能やファイル、もしくはgitでコミット前のコードに対してテストを生成してください。
- 実装からテストを考えるのではなく、バグを見つけることを考え、あるべきテストの形を考えてください。
- バグや改善点を発見して、実装への修正を作成することも歓迎です。
- 実装の詳細ではなく、ふるまいをテストして実装のリファクタリングによってテストへの変更が必要になる脆いテストにはならないよう気を付けてください。
- ファイルアクセスやネットワークなどを介さない場合は、なるべくモックではなく実際のコードを利用してください。
- ユニットテスト、結合テスト、E2Eテストなどテストのサイズを考え、ユーザに作成するテストの提案をしてください。
- すでにテストが存在している場合は、過不足がないかレビューしてください。

## 実装

- テスト対象のオブジェクトなどには`sut`という名前を付けてください。
- テストは1. arrange, 2. act, 3. assertの順で書いてください。それぞれのフェーズの間には改行を必ず挿入してください。
- テストの名前は関数名などではなく、どのようなふるまいをテストしているかを示した名前にしてください。
  - 形式は「期待結果 + `when` + 条件」を基本とします（例: `returns_zero_when_list_is_empty`）。グループ名と続けて読むと文になるようにします（例: `sum` → "sum returns zero when list is empty"）。
  - テスト対象の名前はグループ（後述）が表すため、テスト名で繰り返さないでください。
  - `test_valid_input`や`works_correctly`のように、条件や期待結果が読み取れない名前は避けてください。`should`などの意味のない語も付けないでください。
  - 前提となる状態が複雑な場合は、テスト名に詰め込まず、対象のグループの中にネストしたグループで表してください（例: `mod given_expired_token { ... }`、`describe('when token is expired')`）。
  - プロジェクトに既存の命名規約がある場合はそちらを優先してください（例: Goの`TestXxx` + `t.Run`のサブテスト名にこの形式を適用する）。
- テストは対象の機能・関数・クラスなど論理単位ごとにグループ化し、コメント区切りや言語のモジュール機能（例: Rustの`mod`、`describe`ブロックなど）を使って同一ファイル内で視覚的に分割してください。
